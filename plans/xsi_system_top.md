# Plan: generated XSI system tops, and the host as a hooked module

**Status:** drafted 2026-10-07; Stage 0 done, Stage 1 next. `plans/xrt_target.md` had frozen IPI/XSI;
on 2026-10-07 that was replaced by **two targets** — the Waveflow vocabulary is the general one, XRT
realizes the subset its rules allow, IPI/XSI realizes all of it — and XSI is unfrozen for this plan's
scope.

## Motivation

For a **single composite kernel** the concurrent flow is generated end to end: `tb_top_spec` walks the
Python object, `render_tb_harness` emits the harness, and the gate is bit-exact output plus an exact
cycle count (mem_copy, 2908).

For a **system** — several kernels, slave adaptors, AMD's crossbar, a memory and a host — nothing is
generated. Each example writes its own ~400-line generator script:
[`examples/markov/markov_xsi.py`](../examples/markov/markov_xsi.py),
[`examples/mm_fir/mm_fir_xsi.py`](../examples/mm_fir/mm_fir_xsi.py), `examples/vmac/vmac_build.py`.
Each script holds two kinds of thing:

1. **The RTL top's netlist, restated by hand.** Which stream net joins which kernel port, which
   crossbar slot each `m_axi` takes, which interrupt is a top output, which FIFO sits on which link
   (`markov_xsi.py` `render_top`, lines 179-238). The pysim system already holds every one of these
   facts — its `StreamIF`s, crossbar bindings, adaptors and `IrqIF` lines. The framework helpers for
   the *pieces* exist (`AxiXbarConfig.from_crossbar`, `render_xbar_instance`, `render_adaptor_slot`,
   `mm_writer_gen`, `bus_address_headers`); the walk that joins them does not.
2. **The host program, as C++ inside a Python f-string**, with the scenario baked in as literals
   (`render_tb`, lines 257-406). Its helpers — `ProbePin`, `field_pos`, `parse_kv`, the port matcher
   `_instance` — are copied between examples.

The user's verdict on reading it: *"it is ugly — I could never write this."* An AI agent asked to build
a two-kernel bus system would have to copy-edit one of these scripts, which is the failure this plan
removes.

### The idea: a host is a module with two realizations

A second copy of the host in C++ is **not** the problem. Kernels already have two realizations — the
Python model and the Vitis body — joined by a hook (`kernel_task()`) and held together by a gate. The
host should be treated the same way:

| | kernel | host |
|---|---|---|
| Python realization | `run_iter` / `run_proc` (pysim) | `run_proc` on the `BoundMemSlaveAdaptor` endpoints (pysim) |
| pre-written realization | `kernel_task()` → an `hls::task` body in a `.h` | `bfm_model()` → an `XsiSimObj` in a `.h` **beside the example** |
| what is generated | the top, the wiring | the harness, the wiring |
| the gate that ties them | same vectors, bit-exact output | same scenario, **identical per-endpoint transaction trace** |

The hook already exists: [`bfm_model()`](../docs/guide/custom_hooks/bfm_model.md) ("my cycle model is
*Y*"), with a stated conformance obligation — a byte-identical vector gate. The host simply does not use
it yet, for three reasons this plan fixes: a `BfmModel` must name a class in the framework's
`xsi_bfm.h`; `BFM_DUALS` says no model masters a DUT's AXI slave port (stale — `AxiMmMaster` exists and
both examples use it); and `tb_top_spec` takes one DUT child, not a system.

The C++ side need not be hard to write. `xsi_mm_host.h`'s endpoints (`MmQueueWriter`, `MmQueueReader`,
`MmRegBankCfg`, `IrqPin`) are the C++ twins of the Python host endpoints (`stream_master`,
`stream_slave`, the reg-bank view, `IrqIFSink`), so a host `.h` reads line for line like its Python
`run_proc`.

## Design

**The cut is a set.** `tb_top_spec(tb, dut=...)` today names one synthesized child. A system cut names
the children inside the RTL top — the kernels, the adaptors, the crossbar, an on-chip memory — and
everything else (the host, an off-chip memory as `FlatMemory`) is a BFM beside it. The boundary is still
derived: an endpoint bound to nothing inside the set is a top port.

**The RTL top is generated by walking the system graph** (target name TBD, e.g. `system_rtl_top`):

| graph element | emitted |
|---|---|
| a Vitis kernel child | an instance of its csynth'd module, ports matched from its generated `<top>_ports.h` / `TopSpec` (not a regex over the `.v`) |
| a `StreamIF` between two children | stream wires; a declared depth on a link between *separate* kernels becomes an `mm_sync_fifo` |
| an `AXIMMCrossBarIF` | `generate_axi_xbar` + `render_xbar_instance`; each bound `MMIFMaster` an SI slot, each `MMIFSlave` an MI slot |
| a `MemSlaveAdaptor` / a lone view | `render_adaptor_slot` / `render_view_slot`; its kernel-side streams join the nets above |
| a routed credit stream | the writer kernels `mm_writer_gen` already builds, with `target` from the address map |
| an `IrqIF` crossing the cut | a top output, answered by an `IrqPin` |
| unused pins | tie-off rules, once, in the framework (`s_axi_control_*` low, missing IDs) |

**The host is a hooked module.** It becomes an `HwModule` that declares:

```python
def bfm_model(self):
    return BfmModel("MarkovHost", ports=("m", "irq_qcmd", "irq_qresp"),
                    header="markov_host.h")          # new field: a header beside the example
```

`markov_host.h` is a hand-written `XsiSimObj` built on `MmQueueWriter` / `MmQueueReader`. **No
scenario in the C++**: the jobs reach both hosts from the same file (a burst bundle or a `DynParam`
path), so one scenario drives both backends — the precondition for a gate.

**The conformance gate** is the kernels' gate applied to the host. Every host endpoint, Python and C++,
records what crossed it (words sent on a queue in, words taken from a queue out, regions read) to a
bundle. The gate: for the same scenario, **each endpoint's trace is byte-identical** between the pysim
run and the XSI run. Per endpoint, not globally — the interleaving across endpoints is timing, and
pysim is loosely timed. The RTL cycle count stays an exact gate of its own, as today.

## Non-goals

- **Generating the C++ host from Python.** Rejected for the same reason `BfmModel` exists: extracting
  an FSM from a SimPy process re-derives code that is easier to write and check by hand. The gate, not
  the generator, ties the two together.
- **AXI-Lite / `HostActivated` DUTs under XSI** — a separate hole (`plans/design_cut.md` S7).
- **Driving XSI from the Python host** (Python calling the XSI C API each cycle). Possible later,
  and it is what the XRT plan's "one host script" wants on a board; not needed for this plan.

## Open questions

- **Where memory sits.** markov's shared memory is a BRAM window *inside* the top; mem_copy's is a
  `FlatMemory` BFM *outside*. Is that the cut (the set includes the `MemoryMod` or not), or a property
  of the memory type? Prefer the cut.
- **Probes.** The timing probes (`PROBES` in `markov_xsi.py`) are valuable and per-example. Keep them as
  an optional list of named handshake expressions passed to the top generator.
- **Trace format.** Reuse burst bundles (one per endpoint) or a single tagged log? Bundles, if the
  existing writer/reader cover a host endpoint's shape.
- **vmac** builds its own top too (`vmac_build.py`); fold it in after markov, or leave it.
