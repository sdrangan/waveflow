# Plan: hook-first kernels — generated boundary, hand-written body, shared stimulus

> **Status (2026-10-01): Stages 1, 2, 3 and 5 done, Stage 6 mostly; 0, 4 and 7 open.** D1 to D4 decided
> (2026-10-01, all as recommended): body-only kernels are declared with an
> attribute, the status-schema return is dropped, `stream_inband` is
> converted, and the lab keeps its frame, updated.

## Motivation

The first full blind test (`examples/mcp_test/rotate.md`, PR #209) produced a
correct accelerator. It was bit-exact through cosim, and pysim timing matched
the RTL to the cycle. But it took about 2.4 hours, and much of the cost had
nothing to do with the design:

- **The agent had to write two restricted Python dialects** that get
  translated to C++.
  - The `SeqTB` testbench cannot loop or branch on its own data. The agent
    ended up generating 8 near-identical testbench classes, one per
    (width, transaction count).
  - The `on_start` control loop is extracted into the kernel shell.
- **The `stream_inband` pattern needs two testbenches anyway:** `PolyTB`
  (SimPy) and `PolyTBHls` (`SeqTB`). So the restricted testbench dialect
  bought no single source.
- **The testbench could not send a burst without TLAST,** so error code 4 was
  verified only in pysim.

Meanwhile, what an AI writes quickly and well is ordinary code: a C++
testbench with loops, a Python model, a kernel body.

**The target user for this plan** works in the traditional industry flow, as
do the students in the intro class. They write host-launched (and later
free-running) Vitis kernels. They want a bit-exact Python model that a
system simulation can call, plus the kernel's timing and resources from
csynth and cosim. They do **not** need a discrete-event timing simulation in
Python today. Every one of them will use an AI.

**The goal:** the MCP flow works *robustly* for this user, with performance
not much worse than a flow without Waveflow. Waveflow keeps what it is
genuinely better at:

- generated boundaries and serializers;
- build steps that already parse the reports;
- the verification process;
- an upgrade path to a discrete-event (LT) timing model, without forcing it.

The publishable comparison belongs to the XSI/BFM flow, where stall-accurate
timing is Waveflow's real advantage. It is a separate, later plan; see Stage 8.

## The convention

For most kernels, `HostActivated` now and `FreeRunMod` later:

1. **The user writes a Python module.** It declares ports, widths and the
   register map, and contains no behavior written in a restricted dialect.
2. **The kernel body is a single custom hook:** the whole of `on_start` for
   `HostActivated`, or `run_iter` for `FreeRunMod`.
3. **The user writes the hook's Python model as a pure function plus a thin
   port wrapper.** The pure function (for example
   `rotate_model(cmd, samples) -> (samples_out, status)`) is bit-exact and is
   what a system simulation calls. The wrapper only reads and writes ports
   and calls it.
4. **Waveflow generates the kernel boundary:** the prototype, every
   `INTERFACE` pragma, and a register map that matches Vitis's real layout.
   Its body is one call to the hook (`.tpp`), passing **every** kernel
   argument, register fields included, by reference.
5. **The user or AI writes the C++ hook** against that full argument list,
   using the generated serializers.
6. **The user or AI writes the tests.** Python writes each scenario's
   stimulus to files **once**. A Python driver (the model through the
   wrapper) and a **hand-written C++ testbench** both read those files and
   write their outputs to files. Every output (pysim, csim, cosim) is checked
   against expected results from an **independent** reference, such as the
   spec's worked examples or an oracle written before the hooks. Checking
   the two hooks only against each other is not enough, since one AI wrote
   both.
7. **Optionally, the user or AI adds a timing model to the wrapper** for
   discrete-event simulation. The pure function never changes.

| Generated by Waveflow | Written by the user or AI |
| --- | --- |
| schema headers and serializers (Python and C++, from one declaration) | the schemas themselves |
| kernel prototype, pragmas, register map, the call to the hook | the hook body (C++) and the pure model (Python) |
| build steps: csim, csynth, cosim, report parsing | scenarios, the C++ testbench, the Python driver, the checker |
| the scaffold that sets all of this up | the optional timing model |

**`SeqTB` is not deleted.** It stays working for the examples that use it.
It is simply not on the default path, and it is not taught as the way to
test. Its `if` bug is fixed regardless (Stage 4).

## Stages

### Stage 0: measure today's baseline

So that "not much worse" is a number, not a feeling.

- **A no-Waveflow arm in `blind-test`** (`--no-waveflow`): the same harness,
  but with no Waveflow MCP server and a first message that says to use Vitis
  directly. Python with numpy is available.
- **An independent grader for `rotate.md`** that neither arm writes. It holds
  hidden stimulus files and expected outputs from a reference written by us,
  and adapters that run each arm's final kernel on them in csim. Without it,
  each arm passes its own tests.
- **Run rotate in the no-Waveflow arm** 2 or 3 times. Record wall time,
  tokens, the grader's verdict, error cases covered, and whether timing was
  validated or only reported.

**Gate:** baseline numbers recorded in this plan.

### Stage 1: the code-generation change

- **Pass the register map into a hook.** When a hook parameter is the
  register map, expand it into the kernel's register arguments by reference,
  in top-signature order. Today this fails with "cpp_type: cannot translate
  VitisRegMap" (measured 2026-09-30).
- **Allow a body-only kernel.** A module declares its kernel body (for
  example `cpp_body = "run"`) and writes no `on_start`. The generator emits
  the pragmas plus one call passing every kernel argument. The `.tpp` stub
  states that the body must be inlined.
- **`HostActivated` first.**

**Gate:** a body-only variant of `stream_inband` passes csim **and** csynth,
with every register argument crossing the hook call, and `m_axi`/`s_axilite`
still bound to the top. A spike on 2026-09-30 showed that code generation
already works with a status *returned* from the hook; this gate covers the
by-reference form and Vitis.

> **DONE (2026-10-01, branch `hook-first-s1`).**
> - `HostActivated.cpp_body` names the body. The module writes no
>   `on_start`; one is supplied that runs the Python body in pysim.
> - `extract_kernel` returns a one-call tree for it, so every caller (header,
>   top, stubs, checks) takes the new path.
> - **The hook's C++ parameters are the kernel's own** (`_kernel_arg_decls`,
>   now the single source of the top-level argument order): streams templated
>   on their `HwParam` widths, register fields by reference, `m_axi` pointers.
> - **The stub carries `#pragma HLS INLINE`** and lists the module's schema
>   headers, since the top-level header only includes what the arguments use.
>
> **Gate, all four held on Vitis HLS 2025.1**
> (`tests/build/test_body_only_vitis.py`, `-m vitis`, about 1 min):
> 1. csim byte-identical to the extracted `poly` kernel on the same inputs;
> 2. csynth, II = 1, about 138 MHz estimated;
> 3. register offsets equal the `VitisRegMap` (0x10/0x20/0x30/0x40);
> 4. an early TLAST makes the hook write halted=1, error=3, tx_id=42
>    through the references.
>
> Item 4 needed a hand-written C++ testbench. The generated `SeqTB` one
> always pops `nsamp` samples, so it aborts on an empty stream after a halt:
> one more data point for Stage 2. Fast tests:
> `tests/build/test_body_only_kernel.py`. No regressions: 2,630 passed in
> `tests/build`, `tests/hw` and `tests/examples`, with only the known
> failure deselected.
>
> **Not done, and not needed:** passing the register map into an *ordinary*
> hook called from an extracted `on_start` (the first bullet above). A
> body-only kernel already hands the hook every register field by reference,
> and with D2 there is no other caller. Revisit only if a design needs an
> extracted control loop *and* a hook that writes status.

### Stage 2: shared stimulus and the C++ stream helper

- **The stimulus format.** Extend the existing burst bundle (`burst_io`:
  `words.bin`, `bounds.bin`, `meta.json`) with **a TLAST flag per burst**, so
  a malformed burst can be described. Python writes and reads it.
- **A C++ helper header,** generated next to the others:
  - `wf::play_stream(bundle, s_in)`: push every word with its TLAST;
  - `wf::record_stream(m_out, bundle)`: drain the output, TLAST included.

  A testbench that handles any number of transactions becomes about 20
  lines of ordinary C++.
- **A Python reader** that splits a recorded stream into transactions, for
  the checker.

**Gate:** a toy kernel's csim replays a 3-transaction stream that includes a
burst with no TLAST. Python reads back the identical words and TLAST flags.

> **DONE (2026-10-01, branch `hook-first-flow`).**
> - **Python:** `burst_io` gained an optional `tlast.bin` (one `uint8` per
>   burst; absent means all TLAST, so existing bundles are unchanged byte for
>   byte), plus `StreamBurst`, `write_bursts` and `read_bursts`.
> - **C++:** `waveflow/build/bundle_tb.h` provides `wf::play_stream<W>` and
>   `wf::record_stream<W>` (up to 64-bit words), shipped by `StreamUtilsStep`
>   next to `streamutils_*.h`.
> - **No transaction splitter:** splitting a recorded stream into a design's
>   transactions is design-specific, so the checker does it, not a framework
>   function.
> - **Gate** (`tests/build/test_bundle_tb.py`, `-m vitis`, csim, about 8 s):
>   round-trips at 32 and 64 bits, including values above 2^32. A missing
>   TLAST on the *last* burst survives exactly. A missing TLAST *mid-stream*
>   is recorded merged with the next burst, because TLAST is the only
>   boundary on the wire, so that is what any kernel would see. The helper
>   documents this rather than inventing a boundary.

- an independent checker, and a `run_dag_cli` build with the stock steps;

### Stage 4: the rotate follow-ups this flow needs

From PR #209's list:

- **#6:** several word widths from one module (one shell per width; the hook
  is already a template on width);
- **#1:** the schema validator picks up the abstract `ComplexField` base when
  a file imports it;
- **#2:** `write_uint32_file` fails on a `DataArray[ComplexField]`;
- **#5:** `ArrayUtilsStep` writes a complex element's headers to `.` rather
  than `include/`;
- **#7:** the Vitis steps are always stale;
- **`SeqTB`:** fix the `if` on testbench variables (it looks in the kernel's
  variable table), and make every rejected construct's error say what a
  `SeqTB` can express and point to the hand-written testbench instead;
- **#8:** investigate the nested-project csim link error.

**#4 (no burst without TLAST) is resolved by Stage 2.**

> **DONE (2026-10-01, branch `hook-first-flow`).**
> - **#6 needed no code.** `param_supports = {"bw64": {"in_bw": 64, "out_bw": 64}}`
>   on a body-only module emits `poly` and `poly_bw64`, both calling the one
>   templated body. Measured on Vitis: `poly_bw64` csim bit-exact against
>   `poly_eval` with an odd sample count (half-full last word), csynth II = 1.
>   Documented in `custom_hooks/body_only.md` and `process.md`; a fast test pins
>   the two tops and the single body.
> - **#1:** the validator skips every name the text imports, so a borrowed
>   schema (or the abstract `ComplexField`) is no longer reported as defined.
> - **#2:** `write_uint32_file` takes a `DataArray` and its element type, like
>   `write_array`, with the same mismatch check.
> - **#5:** `ComplexField.specialize` inherits the inner's non-default
>   `include_dir`, so a complex element's array utils land in `include/`.
> - **`SeqTB`:** `if local.field == value` on a schema the TB read or popped now
>   lowers -- it was failing in the extractor (kernel scope) **and** had no TB
>   emitter at all. A `for` / `while`, or an `if` the extractor cannot lower,
>   now says what a `SeqTB` can express and points to `wf::play_stream` and
>   `body_only.md`.
> - **#8 is a Vitis 2025.1 defect, reproduced.** `open_project vitis/w32_t1`
>   records the *design* file relative to a one-level project (`../gen/poly.cpp`,
>   even from an absolute `add_files` path); csim's makefile drops it and the
>   link fails with `undefined symbol: poly(...)`. `cd vitis; open_project w32_t1`
>   works (all five scenarios bit-exact). The rule is in `process.md`.
> - **#7 did not reproduce** in the new structure: the example's steps all go
>   stale and fresh correctly. One trap seen while testing #8 and worth knowing:
>   `--through gen_kernel` does not run `gen_include` (not an ancestor), so a

> - **`run_vitis_hls(args=...)`** now raises at once: `vitis-run` has no

### Stage 8 (later, separate plan): `FreeRunMod` and the comparison

- `run_iter` as a body-only hook, with a reference example.
- **Checks for the `hls::task` traps** a hook author hits. Two are known
  already: a task that writes before it reads keeps counting during reset,
  and a write followed by a blocking read on two streams can deadlock.
- A hand-written XSI/BFM testbench.
- That flow is where the publishable comparison belongs, with a sixth
  requirement: a Python model that stays timing-accurate under input and
  output stalls, validated against RTL driven with the same stall pattern.

## Decisions

- **D1 (DECIDED: as recommended). How a body-only kernel is declared.** Either a class attribute
  (`cpp_body = "run"`, no `on_start`), or a minimal `on_start` that only
  calls the hook. *Recommended: the attribute,* so the Python side is purely
  declarative, with nothing that looks like simulation code to imitate.
- **D2 (DECIDED: as recommended). Keep the status-schema form?** Returning a status schema from the
  hook already works (measured). *Recommended: no.* Once the register map
  can be passed in, one way is enough.
- **D3 (DECIDED: as recommended). Convert `stream_inband`, or add a new example?** *Recommended:
  convert it.* It is what the lab and the scaffold copy, and keeping its
  timing model in the wrapper means it still demonstrates the
  discrete-event upgrade path. The cost is that its docs pages change.
- **D4 (DECIDED: as recommended). Which frame the lab uses.** If `stream_inband` is converted (D3), the
  existing frame is updated rather than a new one added.

## Not in this plan

- Deleting `SeqTB`.
- The XSI/BFM comparison and the stall-accurate timing requirement (Stage 8,
  separate plan).
- Shipping the knowledge corpus in a wheel.
