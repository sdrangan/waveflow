# Recalibration at Vitis / Vivado 2025.1

**Decision (2026-10-29).** The project supports one tool version: **Vitis HLS / Vivado 2025.1**.
Every calibrated model and every number the docs and papers quote is measured with it, on the lab
machine (the RFSoC machine). Nobody keeps a second version installed; the 2024.1 records stay in git
history, not in the tree.

This plan is run on the lab machine, by a student with a Claude Code session in a clone of this
repo. Each stage ends with a commit and a short report back (what ran, what failed, the numbers).
Stop and report rather than improvise when a step fails or a number is far from the expected range.

## Why 2025.1, not 2026.1

- **The license.** The lab machine's Vivado license covers releases up to 2025.1, and it is locked
  to that machine. Vivado synthesis, implementation and bitstreams for the RFSoC board
  (`xczu48dr`) need it, so 2025.1 is the newest version the whole flow -- calibration *and* the
  board -- runs on.
- **What is already at 2025.1.** The development laptop runs 2025.1, `MIN_TOOL_VERSION` in
  `waveflow/toolchain/toolchain.py` is already `(2025, 1)`, and the CG paper's numbers (the vector
  unit 3,447 cycles a job, `CgVectorUnit` 3,581: `examples/vecunit_cg/measured_2025_1.json`) were
  measured with it.
- **Not two versions.** The instructional machines run 2026.1, and calibration alone (Vitis HLS and
  xsim) needs no license, so it could run there. The board flow would still be at 2025.1: two
  versions, which is what this plan removes. Students may use the instructional machines for HLS
  coursework; their cycle and resource estimates will be off by a few percent (the gap measured
  between 2024.1 and 2025.1, below), and they should be told so.

A measured number belongs to a tool version. Between 2024.1 and 2025.1 the vector unit's CG build
changed without any source change: the execute task's decode loop went from II 13 to II 14, the
cycles a CG job from 3,359 to 3,447, FF from 71.7k to 60.7k, BRAM18 from 36 to 40
(`examples/vecunit_cg/measured.json` against `measured_2025_1.json`). The models fitted at 2024.1 do
not describe 2025.1.

## If 2026.1 becomes available

A license for releases past 2025.1 has been requested from AMD. If it arrives:

1. **This plan is run again at 2026.1**, as a new plan (`plans/calib_2026_1.md`) copied from this
   one with the version changed: a new platform `xczu48dr_250mhz_vitis2026_1`, fresh held-out sets
   (the 2025.1 ones will have been scored), every gate and model re-measured, then the 2025.1
   platform retired and `MIN_TOOL_VERSION` raised. The switch is made all at once -- laptop, lab
   machine, docs -- so there is never more than one supported version.
2. **What to expect.** The models' *forms* should carry over and only their coefficients change, as
   from 2024.1 to 2025.1. What may not carry over: rules tied to how a version binds or schedules --
   the vector unit's BRAM count (`_bram18`), its decode-loop II, gates that pin exact cycle counts --
   and HLS behaviors checked only on older versions (`hls::read_buf` / `write_buf` under
   `EXPLICIT_ACQUIRE_RELEASE`, `m_axi` on an `hls::task`). Each is re-checked by Stage 1 and Stage 3
   of the new run, not assumed.
3. **Until then**, the instructional machines' 2026.1 is unsupported: fine for coursework, not for a
   recorded number.

## What is calibrated today

Everything lives on one packaged platform,
`waveflow/calib/platforms/xczu48dr_250mhz_vitis2024_1/` (part `xczu48dr-ffvg1517-2-e`, 250 MHz,
2024.1), named in one place: `PLATFORM` in `waveflow/linalg/cost.py`.

| Component | Models on the platform | Calibration driver | Guide |
|---|---|---|---|
| Systolic unit | `models/systolic_*`, `components/systolic_unit` | `examples/mimo_cg/hw/linalg_cal.py` | `docs/guide/dsp/systolic/` |
| CG vector unit | `models/cg_vector_*`, `components/cg_vector_unit` | `examples/mimo_cg/hw/cg_cal.py` | `docs/guide/dsp/cg_vector.md` |
| Vector unit (`VecUnit`) | `models/vecunit_timing`, `models/vecunit_resources` | `waveflow/vecunit/calib.py`, with the RTL catalogues of `examples/vecunit_cg/cg_measure.py` and `examples/vecunit_mf/mf_measure.py` | `docs/guide/dsp/vecunit/timing.md` |

The systolic *engine* is not on the platform (`docs/guide/dsp/linalg_common.md`, *Cost data*); it is
out of scope here.

## Rules

1. **Pre-register.** The fit and held-out sets are committed before any calibration build runs
   (the rule every driver above already follows). The fit sets are kept. The held-out sets are new
   (below): the old ones have been scored, and the model forms were chosen knowing their results.
2. **Score once.** Each driver refuses to score a held-out set twice; do not work around it. If a
   held-out score misses its target, report it, do not refit.
3. **Name the version.** Every recorded number carries "2025.1".
4. **Do not edit an expected value to make a test pass.** Where a gate pins a cycle count, record the
   old and new value and the reason (a schedule change in csynth's log, say) and report it; the
   change is accepted by review, not by the test.

## Stage 0 -- the lab machine

1. **Upgrade to 2025.1.** The machine runs Linux with Vitis / Vivado 2024.1 under `/tools/Xilinx`.
   Install 2025.1 beside it, with the Zynq UltraScale+ RFSoC devices; check that Vivado 2025.1
   accepts the existing license (a synthesis of a small `xczu48dr` design) and still finds the
   RFSoC 4x2 board files (they are added to the board search path by `~/.Xilinx/Vivado/Vivado_init.tcl`).
   Then uninstall 2024.1.
2. Clone the repo and check out this branch. Create a venv beside it and `pip install -e ".[dev]"`.
3. Write `CLAUDE.local.md` at the repo root (gitignored): the OS, the venv's path and how to run
   pytest through it, the Vitis / Vivado 2025.1 install path, that XSI runs through `run.sh` with the
   system g++, that the RFSoC 4x2 board is attached and where its board files are. If the toolchain
   is not found under `/tools/Xilinx/<version>` or `/opt/Xilinx`, set `WAVEFLOW_VITIS_PATH` and
   `WAVEFLOW_VIVADO_PATH` (`waveflow/toolchain/toolchain.py`). Do not copy the license file or its
   owner into the repo.
4. Run the fast suite: `pytest -m "not vitis and not xsi and not gem5"`. Known failure: the
   knowledge-base index-timing test (it times wall clock). Anything else: report it.

**Report:** OS, Python, the tool version string the toolchain detects, the license check, the fast
suite's result.

## Stage 1 -- the gates at 2025.1

1. `pytest -m vitis`, then `pytest -m xsi`. A skip fails an `-m xsi` session; the gates need a prior
   csynth of each top and skip loudly without it.
2. **The two machines must agree.** The laptop has passed these gates at 2025.1 on Windows
   (`WANT_XSI_GATES` 245). The lab machine runs the same version on Linux: every pinned cycle count
   should match. A difference is a finding (an OS- or compiler-dependent path), not a new expected
   value.
3. Re-test the HLS behaviors so far checked only on 2024.1 and the laptop; each has a gate:
   `hls::read_buf` / `hls::write_buf` under `EXPLICIT_ACQUIRE_RELEASE` (the vector unit's execute
   task), `m_axi` on an `hls::task` (`offset=off` and `stable`), stream-of-blocks locks.

**Report:** a table of every failed or changed gate: test, old value, new value, the csynth log line
that explains it when there is one. No fixes in this stage beyond the environment.

## Stage 2 -- the platform and the pre-registered sets (one commit, before any calibration build)

1. **The new platform.** Create `waveflow/calib/platforms/xczu48dr_250mhz_vitis2025_1/` with a
   `platform.json` copied from the 2024.1 one, `"tool": "Vitis HLS / Vivado xsim 2025.1"`. Point
   `PLATFORM` in `waveflow/linalg/cost.py` at it. Every fit then files there, never into the 2024.1
   directory.
   **Trap:** `waveflow/vecunit/unit.py::_calibrated` silently falls back to default coefficients when
   no `vecunit_timing/params.json` is on the platform, and the linalg `get_rm` refuses a platform
   whose models are missing. Until Stage 5 the branch is in that state on purpose: do not merge it
   before every model is filed.
2. **Held-out sets, new.**
   - Vector unit, timing (`waveflow/vecunit/calib.py`): add `"holdout3"` to `CG_JOBS` (random 6,
     seed 399, `npass` (14, 22, 30), `n_max` 8, solves `[(8, 32, 3, 51), (6, 24, 2, 52)]`) and to
     `MF_JOBS` (random 6, seed 499, `npass` (10, 18), `n_max` 4, `k_max` 64, frames
     `[(160, 4, 71), (96, 7, 72)]`); a `TIMING3_HOLDOUT` of `("cg", "holdout3")`,
     `("mf", "holdout3")`, `("cg_l8", "holdout3")` and the catalogue's steady workloads on every
     build of `BUILDS`.
   - Vector unit, resources: a `RESOURCE_HOLDOUT2` of `(8, 8, 3, "all", "mf")`,
     `(2, 32, 2, "mul1", "cg")`, `(4, 64, 2, "all", "cg")`.
   - Systolic and CG units: a fresh seeded draw of each driver's held-out builds (a new seed in
     `holdout_set` of `linalg_cal.py` and `cg_cal.py`), written by `split` and committed.
3. **The scoring test computes, not reads (review item R7 of `plans/vecunit_future.md`).**
   `tests/vecunit/test_calib.py::test_the_filed_timing_is_what_pysim_charges` asserts the held-out
   mean the JSON records, so it cannot fail. Make it recompute pysim's intervals from the filed
   coefficients against the RTL intervals the record holds. R7 itself (the 2024.1 score) closes when
   the 2024.1 record is retired in Stage 5.

**Report:** the commit; `split --check` of both linalg drivers passing.

## Stage 3 -- the vector unit

**Resources.** For each fit row `i` in 0..9 and each new held-out row, one csynth:
`python -m waveflow.vecunit.calib csynth fit <i> <root>` (and `holdout`, against
`RESOURCE_HOLDOUT2`), each printed JSON saved as `<dir>/fit_<i>.json` / `<dir>/holdout_<i>.json`.
Then `fit-resources <dir>` and `score-resources <dir>`. Expect a few minutes a row. Check before
fitting: DSP is `4 * n_mul * L + 5` and BRAM18 is `_bram18` on every fit row; BRAM is already known
not to be exact at 2025.1 (40 against 36 on the CG configuration), so find how 2025.1 binds the
memories in csynth's report and update `_bram18` and its docstring *before* the fit, and say so in
the report. Targets: 3 % mean, 6 % worst for LUT and FF.

**Timing.** The model kept at 2024.1 is Stage 7's (`VecTiming`, fitted on the CG configuration),
not Stage 9d's by-phase model (`timing.md`, *By phase and configuration: tried, not kept*). Refit
the same form:
1. The RTL catalogues: `python -m examples.vecunit_cg.cg_measure --root <dir>` and
   `python -m examples.vecunit_mf.mf_measure --root <dir>`, recording to new files
   `measured_new.json` beside each script (the 2024.1 `measured.json` stays until Stage 5).
   Add the `holdout3` workloads to their `RUNS`. Each build's csynth and XSI run once; expect hours.
   Every run must be `"exact": true`. **Check:** the CG build's `steady` run must give 3,447 cycles a
   job and the resources of `examples/vecunit_cg/measured_2025_1.json` (the laptop's, same version);
   a difference is reported before going on.
2. Fit Stage 7's form on the CG build's `calib` run from the catalogue (`calibrate_timing` reads an
   RTL root today; give it the catalogue's intervals instead), file it on the new platform, and
   score `TIMING3_HOLDOUT` once.
3. Record each build's execute-loop schedule (`schedule` in the catalogue). If the decode loop's II
   differs between the CG and matched-filter builds, as it did at 2024.1 (13 against 12), the
   matched filter's error will repeat; report it, do not refit.

Targets: 3 % mean, 6 % worst. At 2024.1 the CG scenarios met them and the matched filter's did not.

**Report:** both records' fit and held-out scores, the schedules, the CG `steady` job interval and
resources.

## Stage 4 -- the systolic and CG units

Each driver in turn: `split --check`, `run --role fit` (use `--shard i/n` to split the builds over
sessions), `merge`, `fit` (files on the new platform), `run --role holdout`, `validate`. The
drivers' docstrings give the build space, the bench and the acceptance criteria. Also re-measure
`CgVectorUnit` on CG `steady` (four `8 x 32` solves of three iterations, `W12g8`): it must give the
3,581 cycles a job of `measured_2025_1.json`.

**Report:** each driver's `validate` output.

## Stage 5 -- retire 2024.1

1. Delete `waveflow/calib/platforms/xczu48dr_250mhz_vitis2024_1/`. In both vector-unit examples,
   `measured_new.json` replaces `measured.json`; fold `examples/vecunit_cg/measured_2025_1.json` into
   it (or delete it, if Stage 3 reproduced it) so one catalogue per example remains.
2. `MIN_TOOL_VERSION` stays `(2025, 1)`. The toolchain checks only that minimum today
   (`ToolInfo` in `waveflow/toolchain/toolchain.py`, reported by `waveflow/scripts/test_amd_tools.py`);
   add a warning for a version above it too -- 2026.1 on the instructional machines runs, but is not
   what the platform was calibrated with.
3. Re-run the fast suite, `-m vitis` and `-m xsi`; every gate pins its 2025.1 value.
4. Docs: every number that names 2024.1 is re-measured or removed -- at least
   `docs/guide/dsp/vecunit/timing.md`, `docs/guide/dsp/linalg_common.md` (*Cost data*),
   `docs/guide/dsp/cg_vector.md`, the examples' `timing.md` pages, `docs/evaluation/`, and
   `CLAUDE.md` (its notes on 2024.1 and the `mimo_cg` study). `git grep -n "2024\.1"` finds them.
5. Close the 2025.1 items of `plans/vecunit_future.md` (*For the CG paper* 1 and 2, *The 2025.1
   retest*) with a pointer here.
