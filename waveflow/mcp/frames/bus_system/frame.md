# Bus system frame (read this before the spec)

A **bus system** is several free-running kernels, an on-chip memory and a
software host on one AXI-MM crossbar.  This file says what the frame
**fixes** -- the rules every design in it follows -- and what a spec **must
decide**, which is the checklist Stage 1 answers.  Where the spec and this
frame disagree, the spec wins; say so in Stage 1.

The pattern is command-response (`docs/guide/patterns/command_response.md`);
the rule under every free-running module is stream-only logic behind adaptors
(`docs/guide/patterns/stream_only.md`).  The references are `markov` (two
kernels, a routed credit link, shared memory) and `mm_fir` (one kernel
reached over the bus, a register bank changed mid-stream).

## Fixed by the frame

1. **Every kernel is a `FreeRunMod` whose logic reads and writes only
   streams.**  The bus reaches it through views generated by
   `build_mm_device`: `QueueIn` (the bus writes a stream the kernel reads),
   `QueueOut` (the kernel writes a stream the bus reads), `RegBank` (a
   configuration the host commits, a status it reads) and `CreditIn` (credit
   returned to a kernel that writes another kernel's queue).  A kernel
   declares its views as `mm_views`.  No kernel holds a bus master of its own
   except to reach memory.
2. **Every job is a command carrying `n` and a `tx_id`, and its response
   echoes them.**  Through a pipeline, the command travels with the data and
   the last stage answers.  A configuration change is ordered by an id the
   command names (`mm_fir`'s `cfg_id`), never by timing.
3. **One crossbar (`AXIMMCrossBarIF`); the host is a `SwHost` with one bus
   master (`add_bus_master`), and it never polls.**  Every wait is on an
   `IrqIF` from a view (`add_irq`): room in a `QueueIn`, data in a
   `QueueOut`.  The host bounds its jobs in flight with a `SwSemaphore`.
4. **Links.**  Kernels joined directly use a `StreamIF` or a
   `CreditStreamIF`.  A kernel that writes another kernel's queue over the bus
   uses an `MmCreditStreamIF`, placed with `.place(...)` on the reader's
   `QueueIn` and the writer's `CreditIn`, its credit window covering the
   link's round trip (`docs/guide/interface/axi_mm/credit_streams.md`,
   "Sizing it").
5. **Memory is on-chip**: a `MemoryMod` on a crossbar slave, inside the cut.
   Off-chip memory is out of scope for this frame until
   `plans/offchip_memory.md` lands; a spec that needs it is reported, not
   worked around.
6. **Addresses come from `assign_address_ranges`** and the layouts the views
   generate (`MemSlaveLayout`), never typed by hand -- in Python, in the
   host's C++ twin, or in a testbench.
7. **Verification**, each against the golden outputs of Stage 1:
   - a golden model of every job, independent of the modules;
   - pysim of the whole system, bit-exact;
   - the system DAG through `compare` (`--synth check` for the gate run): the
     same host scenario at RTL under XSI, its bus traces byte-identical to
     pysim's;
   - the RTL cycle count recorded, and pysim's within 5% of it;
   - zero polls: the RTL run's `DONE` line reports `polls=0`.

## Decided by the spec

Stage 1 answers each in one line, or in the block diagram:

- the kernels, each one's job, and each message's schema (command, forwarded
  data, response);
- each link: direct or routed; its depth; for a routed link, the credit
  window and how often credit returns;
- each kernel's views and their order -- this is the address layout;
- the memory: its size, word width, and the regions the host hands out;
- the host: its threads, jobs in flight, what it writes, what it reads back
  and how it checks each response's echo;
- configuration: what the host can change, when, and the id that orders it;
- the scenario -- the jobs the host runs -- and its golden outputs;
- the acceptance numbers the spec adds (cycles, resources), if any.
