# Reference plan: 03 peak detector

What a good plan for [03_peak_detect.md](../03_peak_detect.md) looks like, written from the tree as of
2026-10-16 (main after PR #283), with `stream_kernel` assumed moved to the protocol of
`plans/guide_system_first.md` D9 (Stage 0a).  It is the answer key, never shown to an agent: no spec
links this directory.  It is rough by intent -- the scoring section says what must be there, what may
differ, and what counts against a plan.

## 1. Approach

- **References:** `stream_kernel` for one free-running module on framed streams, its command-response
  protocol (D9: a header on the data, a status stream, fatal errors) and its generated harness;
  `interleaver` (or `memcpy`) for a **composite** of free-running stages joined by internal streams.
- **Pattern:** `docs/guide/patterns/command_response.md` -- the pipeline form ("the command travels with
  the data, the last stage answers") and the variable-length form (a tagged union ending in `END`).
- **Departures it should name:** a data-dependent rate between the stages (neither reference has one);
  a tagged-union output; a search carried across `PF` lanes in one cycle.
- Frame: none fits today (`freerun_pipeline` is built around memory adaptors).  After Stage 4,
  `freerun_pipeline` or `stream_kernel`, depending on how the ladder of frames ends up.

## 3. Interfaces and messages

- **`s_in`**: `Cmd(DataList)` -- `tx_id` U16, `n` U16, `threshold` U32, `window` U16, `dead` U16; the
  metrics an array of U32, `PF` to a word, through the generated array routines.  Each a burst.
- **The wide link** (an internal `StreamIF`, its `depth` the buffer): per input word, the detections it
  produced -- a count (0..`PF`) and `PF` slots of (`index`, `peak`), or a valid mask -- plus the command's
  framing: a header with `tx_id` ahead of a command's words, and an end carrying `count` and any error.
  48 bits a detection, so `PF * 48` plus the count or mask: a width of its own, wider than `WORD_BW`.
  Several layouts are right; the plan must give one and say how `Serialize` learns where a command
  ends and whether it ended in error.  The depth: enough for a burst of detections, sized against the
  sparse density (one per 16 metrics) -- a reasoned number, not a guess.
- **`m_det`**: one burst per command, `START | DET ... | END`, TLAST on `END` (on an early TLAST, on the
  last message written).  Either realization is correct:
  - **(a) `DataUnion`**: a `SchemaRegistry` with `Start`, `Det`, `End` registered at ids 0, 1, 2; a
    `DataUnionHdr` whose 16-bit `schema_id` is the type; fixed size (padded to `Det`).  The code
    accepts id 0 (`SchemaRegistry.register`: non-negative), but the guide page
    `docs/guide/schema/python/dataunion.md` says ids "must be positive integers" -- a doc error to fix.
    A plan that trusted the doc and remapped the tags, or reported the conflict, read carefully;
    record which.
  - **(b) three `DataList`s, each beginning with the tag** (`resp_type`, an `EnumField` of a 16-bit
    `IntEnum`), then that type's fields.
  At `WORD_BW > 32`, whether messages share a word; each layout stated.
- **`m_status`**: `Status(DataList)`, `tx_id` U16 and `status` an `EnumField` (OK, TLAST_EARLY,
  BAD_PARAM); one burst per command, after `END`.

## 4. Verification

- **The golden**: a pure, sequential `detect(m, T, W, D) -> [(index, peak)]`, independent of the
  modules and of `PF`; `expected(cmds)` builds the messages on both outputs from the intents (the
  `stream_kernel` shape: `Cmd` intents -> `stimulus`, `expected`); the worked examples as unit tests.
- **Each stage alone, then the composite** -- the probe this rung exists for:
  - `harness(Detect, ...)`: its wide output checked against a second golden function (the per-word
    detections), at each width -- the lane logic verified where it is, not through the serializer;
  - `harness(Serialize, ...)`: driven by hand-made wide messages, including a dense burst and an error;
  - `harness(PeakDetect, ...)`: the boundary against the golden.
  A plan that verifies only the composite is weaker; one that names `harness` on each stage is the
  answer.
- **The Python model**: `Detect.run_iter` per command: read the `Cmd`, then the metrics a word at a time
  (or `get_array`), the search state carried, per word a wide message; `Serialize.run_iter`: the
  messages out.  An error: the status written, then the firing never returns (or the module refuses
  further input) -- how a free-running module *stops* is open in the framework (Stage 0a), and a plan
  that faces it scores above one that does not.
- **The scenarios**: `workload(kind)` on each module; all eleven, at `WORD_BW` 32, 64, 128 -- each width a
  build (`HwParam`), so three systems, three tops.
- **The build**: codegen (`DataSchemaStep` per schema, `ArrayUtilsStep` for the metric type at each
  width, `StreamUtilsStep`, the composite's top from its children), then `add_system_steps` per width
  and per harness -- `csynth`, `system_rtl`, `scenario`, `pysim`, `system_xsi`, `compare`.  Starts from
  `example:stream_kernel/stream_kernel_build.py::build_dag`, `docs/guide/build/xsi_system.md#running-it`.
- **The HLS bodies**: `Detect` -- one word per iteration at II=1, the `PF`-step search unrolled; the plan
  should see the chain of `PF` dependent compare-update steps as the timing risk and cite
  `docs/guide/vectorization/hls/loop_optimization.md` ("do not decide, compute and commit in one
  iteration") -- e.g. compute per-lane candidates in parallel, resolve them in a second step.
  `Serialize` -- a loop per command writing one output word per iteration.
- **Throughput**: sparse (scenario 11) at `PF` per cycle, from the RTL cycle count or a calibrated timed
  phase per stage (`add_calib_steps`); dense (7b) reported with what limits it -- the serializer's
  output rate, ideally computed beforehand (words per detection over `PF`).

## 5. Gaps a good plan reports

- How a free-running module stops after a fatal error, in pysim and in HLS, and how a gate shows it.
- `DataUnion` is not a `DataSchema` (a stream's `write` serializes only `DataSchema` instances; a union
  goes as `du.serialize(...)` words); no example uses it on a free-running kernel; the id-0 doc error.
- The pipelined-phase helper (`TimedPhase.pipeline` with a `write_array` store) assumes a known output
  size; the detections are not.

## Scoring

**Must have** (each missing item is a fault):

1. A composite `FreeRunMod` of two leaf `FreeRunMod`s and an internal stream -- not one kernel, not
   `HostActivated`.
2. `WORD_BW` as a build parameter, three widths built.
3. Schemas for every message, the wide link included; the boundary fields, widths and order exactly;
   each layout given.
4. An independent, sequential golden with the worked examples; expected outputs from intents.
5. The testbench from `harness`, and the build through `add_system_steps` to `compare`.
6. Hand-written HLS bodies through `kernel_task()`, citing the loop optimization page.
7. All three error paths, each fatal: the owed `DET` and no `END` on an early TLAST; nothing on `m_det`
   for `W = 0` and `n = 0`; the status written; nothing read or answered after.
8. Sparse and dense throughput, each with how it is measured.

**Accept either:** `DataUnion` or tag-first `DataList`s; equal or unequal message lengths (with a
reason); a count or a valid mask on the wide link; throughput by timed phase or by cycle count.

**Counts against a plan:** packing or unpacking words by hand (`feedback-datalist-not-manual-unpack`);
`SeqTB` or cosim as a gate; a hand-written testbench where `harness` does it; a citation that does not
resolve; polling; an error answered and then carried on from.

**Recorded, not scored:** the frame chosen and what led there; whether `harness` is used per stage;
whether `DataUnion` was found and how; whether the lane-chain timing risk was seen; the wide link's
depth and its reasoning; pages read and never reached; tokens and tool calls.
