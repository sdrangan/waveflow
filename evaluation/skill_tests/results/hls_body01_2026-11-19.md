## Two earlier versions of the skill, and why their runs are not the result

1. **`*_leak`:** rule 8's example was the product of `<16, 3>` and `<16, 1>` -- this test's own
   formats. It now states the general form.
2. **`*_v1`:** rule 5 said to declare cross-command state as a `static` with no initializer, "zero at
   power-on" -- and nothing about reset. The spec's `total` counts samples **since reset**, so it needs
   `#pragma HLS reset`; both v1 skill runs (and the first reference) left it out, while both MCP-only
   runs had it, copied from the guide's `stream_kernel` example. The rule was written from a project
   note that the pragma is ignored by Vitis 2025.1. That note was wrong: csynth experiments on
   2026-11-19 showed the pragma does put a static on reset (`if (ap_rst) x <= 0` in the RTL, for
   `bool` and `ap_uint`, in loop, state-machine and write-first bodies), and that csynth prints
   "Register 'x' is power-on initialization" whether or not it did -- the warning the note had read.
   Rule 5, the reference and the sheet (item C4, 44 points in all) were corrected, and the skill arms
   run again.

## What every run did

All four bodies have the reference's shape, nearly line for line:

- one command per call: the `GainCmd` read by its schema first, the `GainResp`, one loop, the `GainStatus`;
- the loop a word per iteration (`i += PF`, `PF = lane_capacity<W>()`), `PIPELINE II=1`, lane arrays
  partitioned, the multiply unrolled;
- the generated lane routines both ways with the tail count, TLAST as `i + PF >= n`;
- the product in `ap_fixed<32, 4>`, assigned to `Out`, saturation counted against the golden's
  `Rounded`;
- `total` the only `static`, under `#pragma HLS reset`, updated once a command.

Every run read `loop_optimization.md` before writing; the MCP-only runs found it, and a reference body
(`stream_kernel`'s `poly_kernel_task.h`), through `waveflow_get_process` / `waveflow_get_example`.

## What differed

- **D3, both Sonnet runs:** the saturation test converts a side to another type the golden does not
  (`(wide_t)r` without the skill, `(rounded_t)y[k]` with it). Harmless.
- **The initializer.** Both MCP-only runs write `static ap_uint<32> total = 0;`, the skill runs no
  initializer. The same RTL either way; not scored.
- **Tokens.** The skill runs took 30% (Opus) and 41% (Sonnet) fewer tokens in, and 31% (Opus) and 19%
  (Sonnet) fewer out. Turns did not move consistently (20 to 18, 18 to 20).

## What the test shows, and what it does not

On this task the guide and the MCP server are enough for both models: the scores are at the ceiling in
both arms, so the test cannot show the skill's effect on the body's shape. The task is close to a
worked example the server hands out (a header, a lane loop, a response), and its one piece of
cross-command state starts with a blocking read, so none of the traps the skill exists for -- a task
that writes first, a request and its reply on two streams, a credit window, a decision in the loop --
comes up. A second test should put one of those in the task.

What it did show: a wrong line in a skill is followed. The v1 skill moved both models off the guide's
correct example and onto its own incorrect rule.

## Waveflow gaps the test found (while it was written, not by the agents)

- **Two fixed-point formats that differ only in rounding or overflow mode get the same generated name.**
  `FixedField.specialize(16, 1)` and `FixedField.specialize(16, 1, q_mode=AP_RND, o_mode=AP_SAT)` are both
  `Fixed16_1`, so their `ArrayUtilsStep`s collide ("a step named 'fixed16_1ArrayUtilsStep' already
  exists"). The test's `Out` was moved to `<16, 2>` to avoid it. A fix renames the array-utils headers of
  existing designs that use a non-default mode, so it needs a plan.
- **`DataArray` arithmetic takes no scalar operand.** Multiplying an array by a gain read from a header
  needs the gain wrapped in a one-element array (the golden does that, with a comment).
- **A wrong claim about `#pragma HLS reset`** in the `rf_repeat_play` / `rf_shot_tx` code comments and
  docs ("Vitis 2025.1 ignored it"), from the misleading csynth warning above. Corrected in the same
  change; those designs keep `config_rtl -reset state`, which resets every register, pipeline registers
  included. Whether the pragmas alone would close their reset trap was never measured.
